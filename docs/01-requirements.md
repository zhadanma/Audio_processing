## 1. 项目概述

### 1.1 背景与目标

本产品是一个**本地离线桌面音乐处理软件**：导入一首歌曲，使用 AI 源分离模型拆出人声、鼓、贝斯、吉他、钢琴等分轨（stem），对每轨独立调节音量/静音/独奏，实时试听混音结果，并将处理后的音频导出。

全部计算在本机完成，不上传任何音频数据。核心价值是"一次分离、随意调音、快速导出"——分离只做一次，之后的调音是零成本的实时混音。

### 1.2 目标用户与使用场景

| 用户 | 典型场景 |
|---|---|
| 音乐爱好者 / DJ | 制作伴奏、去除人声、remix 素材 |
| 乐器练习者 | 静音自己声部以外的轨（如只要鼓+贝斯），或单独循环某段练习 |
| 内容创作者 | 提取纯鼓、纯贝斯等素材用于短视频/直播 |
| 编曲学习者 | 拆解歌曲编配，单独听某个乐器 |

### 1.3 产品定位

- **本地离线**的 Windows 桌面应用（第一优先级平台）
- 消费级"够用且好用"的分轨质量，**非**专业录音室级多轨编辑器
- v1 聚焦流程闭环：**导入 → 分轨 → 调音 → 导出**，不做效果器、编辑、变调等 DAW 功能

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| Stem（分轨） | 从混音中分离出的单一乐器/声部音频 |
| 一级分离 | 用 `htdemucs_6s` 直接从原曲分离出 6 轨：人声/鼓/贝斯/吉他/钢琴/其他 |
| 级联细分 | 对已分离的某一轨再用专用模型进一步拆分（如鼓→底鼓/军鼓/镲） |
| 组（Group） | 级联细分后子轨的父节点，如"鼓"组包含 kick / snare / toms / hh / ride / crash |
| 项目（Project） | 一首歌的处理单元，自包含源文件、全部 stem 文件、混音参数与波形缓存 |

## 2. 项目范围

### 2.1 v1 交付范围

1. 音频导入（常见格式）与项目创建
2. `htdemucs_6s` 六轨分离（GPU 加速，CPU 降级）
3. 级联细分：鼓组细分（DrumSep）、人声主唱/和声细分（Karaoke 模型）
4. 多轨同步播放、逐轨增益/静音/独奏（含组规则）
5. 多轨波形显示、播放头、跳转、缩放
6. 混音导出（WAV/FLAC，MP3 视 ffmpeg 可用性）与单轨批量导出
7. 项目保存/打开/缓存/重新分离
8. 设置（音频设备、计算设备、模型目录、ffmpeg 路径）与首次运行模型向导

### 2.2 非目标（明确排除）

- 模型训练 / 微调
- 旋律/MIDI/乐谱识别与扒谱
- 变调、变速、EQ、压缩、混响等效果处理
- VST 插件宿主、多轨录音
- 网络流媒体导入、云端处理、账号体系
- macOS / Linux 正式支持（架构上不阻断，但不开发、不测试、不承诺）

### 2.3 分离质量预期（需求方共识，需在"关于"页声明）

| 轨道 | 预期 |
|---|---|
| 人声、鼓、贝斯 | 质量高，可用于练习与伴奏 |
| 钢琴、吉他 | 可用，与"其他"轨存在明显串音 |
| 电吉他 / 木吉他细分 | **实验性**，不保证可用性，默认隐藏或标注 |
| 任何轨道 | 残留其他乐器成分是统计模型的固有限制，无法完全消除 |

#### 3.3.1 静音/独奏语义

- 任一轨**静音**后，该轨不发声。
- 全局存在**独奏**时，只有独奏轨发声，其余全部静音；独奏轨自身的静音优先（静音 + 独奏 = 不发声）。
- 独奏可以多选。

#### 3.3.2 组与子轨规则

- 叶子轨有效增益 = 自身增益(线性) × 所有祖先组增益(线性)
- 有效静音 = 自身或**任一祖先**被静音
- 独奏：任一组被独奏时，其全部叶子视为独奏；组内某叶子单独独奏时，该组内其余叶子静音

## 4. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-1 | 性能 | 4 分钟歌曲六轨分离 ≤ 90 s（RTX 4060，CUDA，目标 30~60 s，以 M0 实测校准）；播放零 underrun；音频回调单块处理 < 5 ms（block=2048 @44.1 kHz）；UI 操作响应 < 100 ms |
| NFR-2 | 内存 | 5 分钟歌曲播放态常驻内存 ≤ 700 MB（只加载生效叶子轨）；显存占用不得超出 8 GB，超限需报错而非崩溃 |
| NFR-3 | 兼容性 | Windows 11 x64 为第一目标；Python 3.11 运行环境；GPU 为可选加速项，无 GPU 可完整使用（速度慢） |
| NFR-4 | 可靠性 | 分离/导出均为"临时目录 + 原子落盘"，中断不产生半成品；项目元数据损坏时可从 `.bak` 恢复 |
| NFR-5 | 隐私 | 模型下载完成后全程离线；不上传用户音频；不包含遥测 |
| NFR-6 | 可维护性 | 模型通过适配器接口接入，新增模型不改 UI 层；核心混音数学有单元测试；类型注解全覆盖 |
| NFR-7 | 许可合规 | Demucs(MIT)、PySide6(LGPL)、ffmpeg（LGPL 构建，独立可执行文件分发）；"关于"页列明 |
| NFR-8 | 可扩展性 | 数据模型支持任意深度的分轨树，新增二级/三级细分模型时只加适配器与配置 |

## 6. 音频格式要求

### 6.1 导入格式

| 格式 | 依赖 |
|---|---|
| WAV / FLAC / OGG / AIFF | 内置（soundfile） |
| MP3 / M4A(AAC) / WMA | ffmpeg 解码 |

### 6.2 导出格式

| 格式 | 位深/码率 | 说明 |
|---|---|---|
| WAV | 16 / 24-bit PCM | 默认 16-bit |
| FLAC | 16 / 24-bit | 无损压缩 |
| MP3 | 192 / 256 / 320 kbps | 需要可用 ffmpeg（含编码器） |

导出采样率固定 44.1 kHz（v1）；声道固定立体声。

## 7. 约束与假设

1. 依赖第三方开源模型权重（Demucs、DrumSep、Karaoke 模型），首次使用需联网下载，之后完全离线。
2. 上游模型质量与可用性不受本项目控制；权重源可能变动，需做本地镜像与校验。
3. 依赖 ffmpeg 可执行文件处理压缩格式；分发采用 LGPL 兼容构建（见架构文档 AD-6）。
4. 用户须对自己处理音频的版权负责；产品内不提供任何规避版权的内容获取能力。
5. Python 模型生态（torch/demucs/audio-separator）存在版本兼容敏感性，依赖版本需锁定并经 M0 验证。
